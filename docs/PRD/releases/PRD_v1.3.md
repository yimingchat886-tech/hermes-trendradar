## 0. v1.3 更新摘要

相较 v1.0，本版完成以下收敛；相较 v1.2，本版重点修正飞书表格、外部卡片与 Hermes 观察机制：

1. **内容赛道固定为 AI 赛道**。
2. **目标平台优先级固定为抖音 > 小红书**。其他平台可作为热点与信息源补充，不作为 v1 主生产平台。
3. **v1 重点从“热点 + 对标双线”收敛为“先跑通对标账号追踪”**。系统先完成对标账号更新、转录、拆解、卡片和选题池补充链路；热点信息系统进入 v2。
4. **对标账号规模预估为 20 个**，由内容+技术（内部群）手动维护和分级。
5. **热点信息分级抓取频率后置到 v2**：S/A/B/C 源分级、突发热点捕捉和热点雷达表不纳入 v1 必须跑通范围。
6. **对标账号每日跟踪**。
7. **视频文案转录采用本地 Whisper**。
8. **v1 暂不考虑发布复盘、内部账号复盘评比和基于发布表现的 Agent 学习闭环**，仅预留接口和表结构。
9. **v1 暂不设置 AI 赛道内容风险审核边界**，仅保留扩展字段。
10. **未来会接入正式 RAG 库**，本版提前设计 RAG 接口和数据对象。
11. **项目无商业化计划，会在 GitHub 上开源**。
12. **飞书表格字段与权限设计单独成章讨论**，本版只定义表的职责和数据对象映射；外部群不开放内部表权限。
13. **v1 不按 AI 子赛道或账号定位再细分标签**。AI 赛道统一处理，热点状态标签进入 v2。
14. **对标账号名单保持开放配置**，框架搭建完成后再由内容+技术（内部群）补充；热点源清单进入 v2。
15. **突发热点标准进入 v2**：v1 通知只推异常；v2 再加入突发热点通知。
16. **选题生成存在前置门槛**：完成“选题筛选 Skill 策略”后才开始提交选题；在此之前只沉淀对标账号内容与人工选题动作。
17. **数据保留策略明确**：原始文件保留 2 个月，自身沉淀长期保留用于后续 RAG；视频文件不保留。
18. **修正 Codex 与 Hermes 分工边界**：Codex 负责在开发期把读取飞书表、写回飞书表、调用 MediaCrawler、生成对标内容线索等能力写入 Hermes 工具层；RSSHub / TrendRadar 进入 v2。
19. **飞书表格运行期责任方固定为三类**：脚本生成、Hermes维护、人工。Codex 不作为飞书字段责任方出现。
20. **用户角色收敛为两类群体**：内容+技术（内部群）与社群成员（外部群），不再细分内容负责人、编导、运营、管理员等团队角色。
21. **飞书多维表格定位为内部使用**；v1 只由表 4 对标内容拆解表、表 7 选题池表生成表 9 卡片表内容；表 5 热点雷达表进入 v2，表 8 发布复盘表暂缓。
22. **不自研 Feishu Adapter**：飞书表格读写优先采用官方 Lark/Feishu CLI（`lark-cli`），必要时允许调用官方 API 的薄脚本；项目不封装通用 Feishu Adapter。
23. **新增 Hermes 观察机制**：Hermes 不直接“学习用户”，而是先把用户的选题动作、修改动作、拒绝原因和显式规则沉淀到临时观察表；表 10-12 是否取消、何时沉淀为 Skill，由人工在 v4 或 v5 决议。
24. **开源源码不涉及登录态**：源码、示例和文档不包含平台账号 Cookie、登录态、绕限制说明或批量爬取教程。

## 1. 项目背景

AI 赛道的信息密度高、更新频率快、热点生命周期短。一个新模型发布、一篇 AI 大咖文章、一次产品更新、一个开源项目爆发、一个平台玩法变化，都可能在短时间内形成内容机会。

内容+技术（内部群）长期需要处理两类选题输入：

1. **对标账号信号**：核心竞品、同赛道优质账号、跨赛道灵感账号的内容更新、爆款内容、评论反馈、标题结构、内容结构和选题模式。
2. **热点信息信号**：全网热榜、AI 垂直信息源、长尾社区、专题 RSS、模型发布、产品发布、开源项目、AI 人物观点、行业事件、潜在趋势和正在上升的热点。

单纯依赖人工刷平台存在以下问题：

- 对标账号更新跟踪不及时。
- 新模型、新产品、新论文、新观点等 AI 赛道突发信号容易漏掉。
- 热点信息分散在抖音、小红书、X、GitHub、Hacker News、公众号、博客、新闻站、RSS、社区等多个渠道。
- 热点与对标账号之间没有系统化融合，导致选题判断不稳定。
- 对标账号拆解沉淀不足，无法形成可复用的选题模型。
- 后续接入 RAG 之前，如果前期数据结构不统一，历史沉淀难以复用。

因此，本项目建设一个基于 Hermes 的 AI 赛道内容选题系统，用开源工具完成信息接入和采集，用 Hermes 作为唯一 LLM 决策层完成理解、拆解、归档、选题建议、日报周报和飞书协作。

本轮版本收敛后，v1 只跑通“对标账号追踪 + 拆解 + 卡片 + 选题池补充”闭环。热点信息系统、热点源分级、突发热点捕捉和热点 × 对标融合选题整体进入 v2。

## 2. 产品定位

### 2.1 一句话定义

本系统是一个面向 AI 赛道内容+技术（内部群）的 **内容选题系统**。长期形态包含“对标账号跟踪与拆解”和“热点信息跟踪”两条主线；v1 只交付对标账号追踪主线。

### 2.2 系统只做两件核心事情

#### 事情一：对标账号跟踪 + 拆解

系统持续跟踪用户维护的对标账号库，对账号新增内容、表现数据、评论区、视频文案、封面信息和内容结构进行采集与拆解，识别可复用的选题模式。

v1 对标账号规模：约 20 个。

#### 事情二：热点信息跟踪 + 沉淀（v2）

系统持续跟踪 AI 赛道热点信息，并按热点状态进行分类：

- **及时热点**：已经爆发，需要快速判断是否借势。
- **潜在热点**：当前热度不一定高，但与 AI 赛道、目标账号定位、用户痛点或未来趋势高度相关。
- **上升热点**：热度正在增长，适合提前准备内容。

### 2.3 v1 的产品重心

v1 不追求固定每日选题数量，只先完成一个基础能力：

1. **对标账号更新及时追踪**。

热点信息持续沉淀、突发热点捕捉和热点 × 对标融合选题进入 v2。

### 2.4 用户看到的核心结果

飞书看板和群消息主要呈现：

1. 对标账号新增内容。
2. 对标账号高表现内容拆解。
3. 由对标内容生成的摘要、链接和分析卡片。
4. 基于对标内容的候选选题补充。
5. 可进入人工评审和立项的候选选题。

## 3. 产品目标与指标

### 3.1 v1 目标

v1 需要证明以下判断成立：

1. 系统能持续、稳定地追踪 AI 赛道对标账号。
2. 系统能把对标账号新增内容结构化、转录、拆解并写入飞书。
3. 系统沉淀的数据结构足够标准化，后续可以接入热点系统和正式 RAG 库。
4. Hermes 能基于对标内容生成被内容+技术（内部群）认为有价值的选题补充。

### 3.2 北极星指标

**选题采用率**。

定义：

```text
选题采用率 = 被人工立项的系统推荐选题数 / 系统生成的候选选题数
```

### 3.3 v1 不设置硬性 MVP 目标值

v1 阶段不设置固定选题采用率目标，也不设置每日选题产量目标。

原因：

- 当前阶段重点是数据沉淀和链路稳定。
- 选题产出应先建立在足够稳定的对标账号更新与拆解之上。
- AI 赛道热点存在明显波动，不适合用固定日均选题数衡量早期系统有效性。

### 3.4 v1 观察指标

v1 可以观察但不强制达标的指标：

| 指标 | 含义 |
|---|---|
| 对标账号日更跟踪完成率 | 每日成功抓取并处理的对标账号比例 |
| 对标内容拆解完成率 | 已采集内容中完成 Hermes 拆解的比例 |
| 高表现内容捕捉数 | 满足点赞/评论阈值的对标内容数量 |
| 证据不足内容数 | 缺少评论、播放量等指标但仍入表的对标内容数量 |
| 选题建议生成数 | Hermes 基于对标内容生成的候选选题数量 |
| 选题采用率 | 选题被人工立项的比例，作为长期北极星观察指标 |
| RAG 可入库率 | 已结构化内容中满足未来 RAG 入库标准的比例 |

### 3.5 对标内容高表现阈值

v1 暂定规则：

- 点赞数 > 1000，进入“高表现候选”。
- 评论数 > 200，进入“高讨论候选”。
- 同时满足点赞数 > 1000 且评论数 > 200，进入“强爆款候选”。

该阈值作为 v1 统一默认规则。后续可按平台、账号等级、账号体量和近期均值进行差异化调整。

## 4. 用户角色与群划分

v1 不再细分内容负责人、编导、运营、管理员等多团队角色，只保留两个使用边界：

### 4.1 内容+技术（内部群）

内部群是系统建设、配置、审核和运行观察的主空间。

职责：

1. 维护对标账号库和 S/A/B/C 分级。
2. v1 维护对标账号和相关采集源；热点源、RSSHub 源、TrendRadar 源和 GitHub Watch 源进入 v2。
3. 查看内部飞书多维表格，包括信息源表、健康表、对标拆解表、素材沉淀表、选题池表和规则库；热点雷达表进入 v2。
4. 确认哪些内容进入素材沉淀表和未来 RAG。
5. 在选题筛选 Skill 完成前，人工维护选题池中的“选题标题”字段，由 Hermes 补充其余分析字段。
6. 查看 radar-ops 异常提醒，包括信息源异常、采集失败、Whisper 转录失败、飞书写入失败等。
7. 审核 Hermes 沉淀出的显式规则、样例库和候选执行策略。

### 4.2 社群成员（外部群）

外部群是内容卡片的消费和反馈空间。社群成员不直接访问内部多维表格的完整数据，不开放内部表权限；只看到由内部表记录生成并写入外部群卡片表的卡片。

可见内容：

1. 对标内容卡片：由表 4 对标内容拆解表生成。
2. 热点雷达卡片：由表 5 热点雷达表生成，v2。
3. 选题卡片：由表 7 选题池表生成；v1 暂定以人工维护标题为主。
4. 发布复盘卡片：由表 8 发布复盘表生成；v1 暂缓。

可执行动作：

1. 查看卡片。
2. 收藏 / 标记有价值。
3. 提交标题修改建议。
4. 提交选题采用或拒绝原因。
5. 提交显式规则，例如“以后类似某类 AI 新模型发布优先做教程型选题”。

上述动作通过外部群卡片交互、群消息或人工收集进入系统，不通过开放表权限直接写入内部表或卡片表。

限制：

1. 不直接修改内部源表、对标账号表、热点雷达原始记录和系统配置。
2. 不获得内部表权限，也不获得卡片表编辑权限。
3. 不通过聊天修改 Agent 配置。
4. 不直接触发采集器或修改工具层。

## 5. 总体架构

### 5.1 架构原则

本项目采用 **“单主脑、多工具”** 架构。

- Hermes 是唯一 LLM 决策层，负责运行期内容理解、对标拆解、热点归类、选题建议和飞书推送。
- Codex 是开发期工程执行者，负责把读取飞书表、写回飞书表、调用 MediaCrawler、生成对标内容线索等能力实现进 Hermes 的工具层；RSSHub / TrendRadar 进入 v2。部署后由 Hermes 在运行期调用这些工具。
- MediaCrawler 只作为工具层或数据源层；RSSHub、TrendRadar 从 v2 开始作为工具层或数据源层。
- RSSHub、TrendRadar、MediaCrawler 不分别接入独立 LLM。
- 所有热点理解、对标拆解、选题生成、日报周报、风险判断，统一由 Hermes 完成。
- 工具层通过 `trend-cli` / `trend-mcp` 暴露标准化能力给 Hermes 调用。
- 飞书多维表格由 Hermes 通过官方 Lark/Feishu CLI（`lark-cli`）维护；v1 不自研 Feishu Adapter。
- 原始数据、全文、转录文本和历史版本保存在本地 DB / 对象存储，飞书只展示摘要、链接、状态和人工操作字段。

### 5.2 信息链路 A：热点与 RSS 信息源（v2）

```text
RSSHub
  ↓
TrendRadar
  ↓
trend-cli / trend-mcp
  ↓
Hermes LLM
  ↓
飞书多维表格
```

说明：

- 本链路不纳入 v1 必须跑通范围。
- RSSHub 是“可订阅信息源接入层”，用于补足 TrendRadar 原生热榜之外的垂直、长尾、专题、账号动态和社区信息。
- 凡 TrendRadar 原生稳定支持的平台，热榜优先走 TrendRadar 原生。
- RSSHub 只做补充，不替代 TrendRadar 原生热榜。
- TrendRadar 负责原生热榜、RSS 内容接入、基础关键词匹配、热点聚合和基础雷达能力。
- `trend-cli` / `trend-mcp` 负责把 TrendRadar 结果标准化为 Hermes 可调用工具。
- Hermes 对热点进行理解、归类、去重、摘要、标签化、沉淀和选题生成。

### 5.3 信息链路 B：对标账号跟踪与拆解

```text
MediaCrawler
  ↓
trend-cli / trend-mcp
  ↓
Hermes LLM
  ↓
飞书多维表格
```

说明：

- MediaCrawler 在 v1 中定位为内部研究与开源验证工具，用于验证对标账号采集链路。
- MediaCrawler 采集结果进入本地 DB / 对象存储，再通过 `trend-cli` / `trend-mcp` 以标准结构提供给 Hermes。
- Hermes 负责对标内容拆解、评论洞察、选题模型提取、可复用角度生成。
- 对标账号采集结果不直接推送到飞书；必须经过 Hermes 处理后入表。
- 视频文案通过本地 Whisper 完成转录，转录结果进入本地 DB，并可作为未来 RAG 语料。

### 5.4 推荐的开源使用方式

| 组件 | v1 使用方式 | 推荐理由 |
|---|---|---|
| RSSHub | v2 接入，v1 暂缓 | 统一接入长尾、垂直、专题、社区和账号动态信息源 |
| TrendRadar | v2 接入，v1 暂缓 | 复用其热榜聚合、RSS、推送、趋势监控和 MCP 能力，但不让其承担最终 LLM 判断 |
| MediaCrawler | 内部研究 / 验证型采集工具；开源发布时需明确边界 | 用于验证对标账号抓取、评论抓取、主页监控和字段结构 |
| Whisper | 本地转录服务 | 对抖音、小红书等视频内容生成可分析的视频文案 |
| trend-cli / trend-mcp | 自建工具适配层 | 屏蔽底层工具差异，统一鉴权、日志、Schema、错误处理和工具调用接口 |
| Hermes Agent | 唯一主脑与 LLM 决策层 | 统一完成理解、拆解、融合、选题、日报周报 |
| Lark/Feishu CLI（`lark-cli`）+ 官方 API | 飞书多维表格读写层 | 优先采用官方 CLI；CLI 不覆盖时允许官方 API 薄脚本，仍不自研 Feishu Adapter |
| Codex | 开发期工程执行者 | 负责实现、修复、测试、重构、文档、部署与 PR；不作为部署后的飞书字段责任方 |

### 5.5 开源发布策略

本项目无商业化计划，会在 GitHub 上开源。

建议开源仓库按模块拆分：

```text
hermes-trendradar/
  apps/
    agent-orchestrator/       # Hermes Agent 编排与提示词/任务配置
    trend-cli/                # 工具调用 CLI
    feishu-cli-scripts/       # lark-cli / 官方 API 调用脚本、表 ID 配置和幂等写入规则
  packages/
    schemas/                  # 统一数据模型
    rag-exporter/             # RAG 导出接口
    dedup/                    # 去重与事件聚类逻辑
  connectors/
    trendradar-adapter/       # TrendRadar 读取适配
    rsshub-adapter/           # RSSHub 源配置/读取适配
    mediacrawler-adapter/     # MediaCrawler 结果读取适配，不建议直接内嵌其代码
    whisper-transcriber/      # 本地 Whisper 转录封装
  docs/
    PRD/
    architecture/
    feishu-tables/
    runbooks/
```

许可证策略已确认采用“主仓库 AGPL-3.0-or-later + 第三方服务 Adapter 化”的稳健路线。原因是本项目是服务端长期运行系统，且会围绕 RSSHub、TrendRadar 等 GPL / AGPL 生态做集成；采用 AGPL 可以减少后续许可证兼容争议，也符合“开源、无商业化”的项目定位。

同时，v1 仍建议坚持以下边界：

1. 不直接复制 RSSHub、TrendRadar、MediaCrawler 的大段源码进入主仓库。
2. RSSHub、TrendRadar 作为 v2 外部服务或可选依赖运行；v1 先不接入。
3. 主项目只维护第三方数据源 Adapter、Schema、CLI、MCP 工具、`lark-cli` 调用脚本、Hermes Agent 配置和文档。
4. MediaCrawler 仅作为内部研究 / 验证型采集工具，开源仓库中默认不内置账号 Cookie、平台登录态、代理配置或绕过平台限制的说明。
5. 源码、示例数据和开源文档不涉及登录态；最小 demo 使用手工样例或脱敏假数据。
6. 若后续决定只保留 Adapter、不复制任何 GPL / AGPL 项目代码，主仓库也可以改为 Apache-2.0 或 MIT；但在当前“基于开源生态设计并长期服务端运行”的前提下，AGPL-3.0-or-later 是更保守、更一致的选择。


### 5.6 Codex、脚本生成与 Hermes 分工边界

本项目需要明确区分 **开发期工程执行**、**部署后脚本生成** 与 **运行期 Hermes 管理**。

一句话原则：

```text
Codex 负责在开发期把能力写进 Hermes 的工具层；
脚本生成负责在运行期产生确定性字段和工具输出；
Hermes 负责在运行期调用工具、理解信息、维护分析字段和生成卡片；
人工负责最终配置、确认、修改、采纳和拒绝。
```

#### 5.6.1 Codex 开发期职责

Codex 是开发期工程执行者，不是运行期字段责任方，也不直接参与飞书表格的日常维护。

Codex 负责把以下能力实现进 Hermes 可调用的工具层：

| 能力 | 开发期实现要求 | 部署后调用方 |
|---|---|---|
| 读取飞书表 | 通过官方 `lark-cli` 优先实现表 ID 映射、字段读取、分页和权限错误处理；必要时用官方 API 薄脚本兜底；不自研 Feishu Adapter | Hermes / 脚本任务 |
| 写回飞书表 | 通过官方 `lark-cli` 优先实现新增记录、更新记录、状态回写、失败重试和幂等写入；必要时用官方 API 薄脚本兜底 | Hermes / 脚本任务 |
| 调用 RSSHub | v2 实现 RSSHub Adapter、源解析、健康检查、标准化输出 | Hermes / 脚本任务 |
| 调用 TrendRadar | v2 实现 TrendRadar Adapter、热点结果读取、事件聚类接口 | Hermes / 脚本任务 |
| 调用 MediaCrawler | 实现 MediaCrawler 结果读取、字段映射、增量同步、异常处理 | Hermes / 脚本任务 |
| 调用 Whisper | 实现本地转录、转录状态、转录结果入库 | Hermes / 脚本任务 |
| 生成内容线索 | 实现标准化 `ContentSignal` / `HotSignal` / `BenchmarkContent` 输出 | Hermes |
| RAG 预留 | 实现 JSONL 导出、DB View、RAGDocument 生成和未来向量库接口 | 脚本任务 / Hermes |
| 日志与可观测性 | 实现任务日志、错误日志、健康检查、异常码、告警事件 | radar-ops |

Codex 不负责：

1. 不判断某个热点是否适合当天做。
2. 不决定选题是否进入飞书选题池。
3. 不作为飞书字段里的责任方。
4. 不直接管理内部群或外部群。
5. 不通过聊天修改生产配置。
6. 不在运行期替代 Hermes 做日报、周报和选题解释。
7. 不直接读取或散播平台账号敏感凭据。

#### 5.6.2 部署后的运行期责任方

部署后，飞书表格与卡片中的字段责任方只允许出现以下三类：

| 责任方 | 定义 | 典型字段 |
|---|---|---|
| 脚本生成 | 由定时任务、CLI、Adapter、同步脚本或确定性程序生成，不包含 LLM 判断 | ID、原始链接、抓取时间、平台指标、任务状态、错误码、内容哈希、本地 DB 路径、RAG Document ID |
| Hermes维护 | 由 Hermes 运行期调用工具后生成或维护，包含摘要、判断、拆解、推荐、卡片文案和规则候选 | AI 摘要、热点状态、对标拆解、评论洞察、沉淀建议、选题补充字段、卡片摘要、拒绝原因归纳 |
| 人工 | 由内容+技术（内部群）或社群成员显式操作产生 | 信息源启用、账号等级、是否沉淀、选题标题、是否采纳、拒绝原因、显式规则、字段删改确认 |

#### 5.6.3 Hermes 管理范围

Hermes 是运行期主脑和内容决策层。

Hermes 负责：

| 模块 | Hermes 职责 |
|---|---|
| trend-chief | 面向内容+技术（内部群），生成日报、周报、热点提醒、卡片摘要和选题建议。 |
| radar-ops | 面向内容+技术（内部群），只推送信息源异常、工具异常、抓取失败、飞书写入失败等运行问题。 |
| competitor-analyst | 默认不接群，处理对标账号更新，拆解内容结构、评论洞察、标题钩子和可复用角度。 |
| 热点理解，v2 | 将 TrendRadar / RSSHub / GitHub 信号归类为及时、潜在、上升。 |
| 突发热点判断，v2 | 基于权威源、多 S/A 源重复出现、GitHub star 短期增长等信号提升优先级。 |
| 对标拆解 | 基于 MediaCrawler 和 Whisper 输出生成对标内容拆解。 |
| 信息沉淀 | v1 判断哪些对标内容建议进入对标拆解表、素材沉淀表和未来 RAG 语料；热点雷达表进入 v2。 |
| 选题补充 | 在用户维护选题标题后，补充推荐理由、关联素材、钩子、大纲、证据链和卡片文案。 |
| 卡片生成 | 将表 4、表 5、表 7、表 8 的内部记录转换为外部可读卡片。 |
| 观察用户动作 | 归纳用户的选题动作、修改动作、拒绝原因和显式规则，写入临时规则库与样例库，后续人工沉淀为 Skill。 |

Hermes 不负责：

1. 不修改源代码。
2. 不创建数据库迁移。
3. 不直接调整底层采集器实现。
4. 不直接绕过权限新增数据源。
5. 不通过普通聊天修改 Agent 配置。
6. 不自动发布内容。
7. v1 不基于用户行为进行不可审计的模型学习。

#### 5.6.4 接口方式

```text
Codex 开发工具层能力
  ↓
trend-cli / trend-mcp / DB schema / lark-cli scripts / official API scripts / MediaCrawler Adapter
  ↓
脚本任务生成确定性字段
  ↓
Hermes 运行期调用工具并维护分析字段
  ↓
内部飞书多维表格
  ↓
卡片表 / 外部群卡片
  ↓
用户动作、修改、拒绝原因、显式规则
  ↓
临时规则库与样例库
```

接口规则：

1. 所有工具必须提供稳定 JSON Schema。
2. Hermes 只消费工具输出，不依赖工具内部实现。
3. Hermes 的 Prompt、Skill、Agent 配置由仓库文件管理，不允许普通群成员通过聊天改写。
4. 所有 Hermes 写入飞书的内容必须带 `source_id`、`object_id`、`task_id`，方便追溯到脚本任务、工具输出和本地 DB 记录。
5. 飞书字段的 `maintainer_type` 只能取 `script_generated`、`hermes_managed`、`manual` 三类。

## 8. 热点信息源与标签体系

本章为 v2 预留设计。v1 不接入 RSSHub / TrendRadar，不建设热点雷达，不做热点源分级抓取；仅在对标账号内容中保留可供后续热点系统复用的关键词、标签和来源字段。

### 8.1 热点状态标签

v2 使用三类核心热点状态：

| 标签 | 定义 | 处理策略 |
|---|---|---|
| 及时热点 | 已经爆发，需要快速判断是否借势 | 进入日报和必要时即时提醒。 |
| 潜在热点 | 当前热度不一定高，但与 AI 赛道和目标受众高度相关 | 沉淀到热点雷达表，后续观察是否上升。 |
| 上升热点 | 热度正在增长，可能形成内容机会 | 提高优先级，进入选题观察池。 |

### 8.2 热点源分类标签

后续热点源按以下方向进行设计：

1. **公共热点**：微博、抖音、小红书、知乎等泛平台热榜中的 AI 相关热点。
2. **行业热点**：AI 模型、AI 产品、AI 公司、AI 开源项目、AI 应用案例。
3. **用户痛点**：AI 工具不会用、效率焦虑、替代焦虑、提示词、办公自动化、AI 副业等内容机会。
4. **政策风险**：AI 监管、版权、数据安全、模型安全、平台规则变化。v2 只打标签，不做强审核。
5. **竞品动态**：对标账号、竞品产品、竞品内容栏目、竞品活动。
6. **平台机制**：抖音、小红书等平台内容机制变化、内容形式变化、流量倾向变化。

### 8.3 AI 赛道标签策略

v1 不按 AI 子赛道、账号定位或内容栏目做强制标签拆分；热点源分类从 v2 开始启用。

处理原则：

1. 产品层面只保留“AI 赛道”这一统一赛道。
2. 热点状态“及时 / 潜在 / 上升”进入 v2。
3. 热点源分类“公共热点 / 行业热点 / 用户痛点 / 政策风险 / 竞品动态 / 平台机制”进入 v2，用于信息源治理。
4. AI 专属关键词可以作为系统自动提取的 `keywords` 或 `ai_tags`，但不作为 v1 的人工配置负担。
5. 后续如果进入多账号矩阵或多内容栏目，再引入 AI 子赛道标签。

可自动识别但不强制维护的 AI 关键词包括：

- 新模型发布
- 大模型能力更新
- AI 产品发布
- 开源项目爆发
- AI Agent
- AI 编程
- AI 工作流
- AI 办公效率
- 多模态
- AI 人物观点
- 论文 / 技术路线

### 8.4 信息源分级与抓取频率

| 信息源等级 | 定义 | v2 抓取频率 |
|---|---|---|
| S 级 | 强相关、强时效、强选题价值信息源 | 小时级抓取。 |
| A 级 | 高价值信息源 | 每日三次。 |
| B 级 | 一般灵感源 | 每日一次。 |
| C 级 | 观察源 | 每日一次或低频抓取。 |

### 8.5 突发热点捕捉机制

除常规抓取频率外，v2 需要预留突发热点捕捉机制。

v2 可采用以下突发热点触发标准：

1. **权威源发布**：AI 公司、模型团队、核心开发者、重要研究机构、重要开源组织发布新模型、新产品、新论文、新功能或关键观点。
2. **多个 S/A 源同时出现**：同一事件在多个高价值信息源中短时间重复出现。
3. **GitHub 项目短时间 star 增长明显**：尤其是 AI Agent、模型推理、多模态、开发工具、工作流自动化等项目。
4. **对标账号跟进前发现**：突发热点机制的目标不是等对标账号做完再发现，而是在对标账号跟进前提前捕捉潜在内容机会。
5. **潜在热点挖掘能力预留**：v2 先记录接口和数据结构，后续再设计潜在热点挖掘策略。

典型突发热点包括：

- 新模型发布。
- 重要 AI 产品发布。
- AI 大咖发布长文、视频或观点。
- GitHub 项目短时间爆发。
- AI 公司重大更新。
- 抖音 / 小红书上 AI 相关内容突然高互动。

建议机制：

1. **S 级源小时级巡检**。
2. **AI 关键词触发**：如 “发布”、“上线”、“开源”、“模型”、“Agent”、“推理”、“多模态”、“Sora”、“Claude”、“Gemini”、“GPT”、“DeepSeek”、“Qwen”等。
3. **关键人物 / 机构 Watchlist**：对 AI 大咖、模型公司、开源组织、重要产品账号配置更高优先级。
4. **跨源重复出现触发**：同一事件在多个 S/A 级信息源出现时自动提升为“上升热点”。
5. **GitHub 增长触发**：GitHub 项目短时间 star、fork、issue、PR 或社区讨论增长明显时，生成潜在热点记录。
6. **对标账号跟进触发**：若多个 S/A 级对标账号开始讨论同一主题，则提升优先级，但该信号不应是唯一触发条件。

### 8.6 信息源健康状态表

v1 信息源健康只覆盖 MediaCrawler、Whisper、飞书写入和脚本任务；RSSHub / TrendRadar 信息源健康从 v2 开始由 `radar-ops` 监控，并写入内部群管理表。

监控字段包括：

- 信息源 ID
- 信息源名称
- 信息源等级
- 最近成功抓取时间
- 最近失败时间
- 连续失败次数
- 最近抓取条数
- 异常原因
- 是否启用
- 负责人
- 备注

## 9. 数据存储与历史版本策略

### 9.1 存储原则

飞书不是原始数据仓库。飞书只放摘要、链接、状态、评分和人工操作字段。

原始数据存储在：

- 本地数据库：结构化元数据、内容索引、状态、关联关系。
- 对象存储：全文、图片、封面、转录文本、评论原文、历史版本。
- 未来 RAG 库：清洗后的可检索语料。

v1 数据保留策略：

1. 原始文件默认保留 2 个月。
2. 项目自身沉淀内容长期保留，用于后续 RAG。
3. 视频文件不长期保留；视频只作为 Whisper 转录输入，转录完成并校验后可删除。
4. Whisper 转录文本、清洗文本、摘要、结构化拆解、热点记录、选题记录可以长期保留。
5. 进入 RAG 的清洗语料不随原始文件清理而删除。

### 9.2 全文抓取策略

全文分级抓取：

| 内容等级 | 是否抓全文 | 是否保留历史版本 |
|---|---|---|
| S 级源内容 | 是 | 是 |
| A 级源内容 | 是 | 是 |
| 进入热点雷达内容 | 是 | 是 |
| 进入选题池内容 | 是 | 是 |
| B/C 级普通内容 | 视情况 | 否 |

### 9.3 历史版本策略

只对以下内容保留历史版本：

1. S/A 级信息源内容。
2. 进入热点雷达的内容。
3. 进入选题池的内容。
4. 高表现对标内容。
5. 未来被标记为 RAG 高价值语料的内容。

B/C 级普通内容默认不保留版本。


### 9.4 视频文件处理策略

v1 不保留视频文件。

处理流程：

```text
视频临时下载 / 读取
  ↓
本地 Whisper 转录
  ↓
生成 transcript 与 clean_text
  ↓
写入本地 DB / 对象存储
  ↓
删除视频临时文件
```

保留内容：

- 视频原始链接。
- 封面链接或封面摘要。
- Whisper 转录文本。
- 分段转录文件。
- Hermes 清洗摘要。
- 对标拆解结果。

不保留内容：

- 视频原始文件。
- 长期缓存的视频中间文件。

## 10. 去重与事件聚类

v1 需要设计自动去重，避免同一对标内容重复入表；热点与跨源事件聚类进入 v2。

### 10.1 去重层级

1. **URL 去重**：完全相同链接视为同一内容。
2. **平台 ID 去重**：同一平台内容 ID 视为同一内容。
3. **标题相似度去重**：标题高度相似时合并。
4. **语义去重**：标题不同但语义一致时合并为同一内容候选。
5. **跨平台事件聚类，v2**：同一事件在多个平台出现时，合并为一个 `event_id`。

### 10.2 去重后保留策略

合并后保留：

- 最早发现时间。
- 最新出现时间。
- 所有来源链接。
- 来源平台列表。
- 最高热度来源。
- 代表标题。
- 关键词集合。
- Hermes 统一摘要。

## 12. RAG 接口预留设计

### 12.1 设计目标

v1 不直接实现正式 RAG 库，但对标内容数据对象必须为后续 RAG 做准备。RAG 删除、撤回和重建策略等到正式 RAG 搭建时再讨论，当前不纳入 v1。

后续 RAG 需要支持：

1. 检索对标账号历史内容。
2. 检索历史热点，v2 后。
3. 检索视频转录文案。
4. 检索历史选题建议。
5. 检索某类 AI 标签下的内容沉淀。
6. 支持 Hermes 在生成选题前查询历史相似内容。
7. 支持避免重复选题。

### 12.2 RAG 入库条件

内容满足以下条件之一，可标记为 `rag_ready = true`：

- 来自 S/A 级对标账号内容。
- 进入热点雷达表，v2 后。
- 进入选题池。
- 对标内容达到高表现阈值。
- Hermes 判断具有长期参考价值。
- 人工标记为值得沉淀。

### 12.3 RAG 输出接口

v1 预留以下接口形式：

1. **JSONL 导出**：按对象类型导出 `RAGDocument`。
2. **DB View**：从本地 DB 提供 `rag_documents_view`。
3. **CLI 命令**：`trend-cli rag export --type benchmark_content --since 2026-06-01`。
4. **MCP 工具**：`search_rag_ready_documents`、`get_rag_document_by_id`、`list_rag_corpus_status`。

### 12.4 RAG 语料分组

建议未来 RAG 库分为以下 collection：

- `ai_hot_signals`，v2 后。
- `ai_benchmark_contents`
- `ai_video_transcripts`
- `ai_topic_candidates`
- `ai_account_profiles`
- `ai_source_profiles`

## 13. Hermes Agent 设计

### 13.1 Agent 总原则

v1 只设计三个 Agent。

- Agent 在本地运行。
- 不允许普通用户通过聊天修改 Agent 配置。
- 配置变更由内容+技术（内部群）在本地配置文件 / 后台完成。
- Agent 的输出必须写入日志。
- 所有 Agent 共用 Hermes 作为主 LLM 决策层。

### 13.2 trend-chief

定位：内容+技术（内部群）主 Agent。

接入：内容+技术（内部群）群。

职责：

1. 推送每日对标账号更新摘要。
2. 推送每周对标账号观察总结。
3. 推送值得关注的对标内容选题建议。
4. 对对标内容进行简要解释。
5. 将高价值对标内容补充到飞书选题池字段。

不负责：

- 修改信息源配置。
- 修改对标账号库。
- 修改抓取频率。
- 修改 Agent 策略。

### 13.3 radar-ops

定位：系统运行与信息源健康 Agent。

接入：内容+技术（内部群）。

职责：

1. v1 监控 MediaCrawler / Whisper / 飞书 CLI / 官方 API 脚本运行状态。
2. v2 再监控 RSSHub / TrendRadar 信息源健康状态。
3. 推送抓取失败、连续失败、数据量异常、频率未达标等异常；v2 再推送突发热点。
4. 维护内部群管理的数据源健康表。

v1 只推送异常，不推送内容选题；v2 通知范围增加突发热点。

### 13.4 competitor-analyst

定位：对标账号分析 Agent。

接入：默认不接群。

职责：

1. 每日处理约 20 个对标账号更新。
2. 调用 MediaCrawler 结果读取接口。
3. 调用本地 Whisper 转录视频文案。
4. 结构化对标内容。
5. 拆解高表现内容和新增内容。
6. 写入对标内容拆解表。
7. 将高价值拆解结果提供给 trend-chief 生成日报或选题建议。

## 14. 飞书多维表格与卡片设计

### 14.1 设计原则

飞书多维表格是内部使用的运行期控制台，不是原始数据库，也不是完整公开内容库。

原则：

1. 内部多维表格给 **内容+技术（内部群）** 使用。
2. 外部社群成员不直接访问内部多维表格完整数据。
3. v1 只将表 4、表 7 的内容制作成卡片后写入外部群的表 9 卡片表。
4. 表 5 热点雷达表进入 v2；表 8 发布复盘表暂缓，仅预留结构。
5. 表 7 选题池 v1 暂定由用户维护选题标题字段，其余字段由 Hermes 补充。
6. 素材沉淀表必须人工确认后才进入长期沉淀或未来 RAG。
7. Hermes 不直接“学习用户”，而是把用户动作、修改、拒绝原因和显式规则先沉淀到表 10-12；是否大版本取消这些表并沉淀为完整 Skill，由人工在 v4 或 v5 决议。

飞书只存放：

- 摘要。
- 原始链接。
- 关键指标。
- 状态。
- 人工判断字段。
- Hermes 结论。
- 卡片展示字段。
- 临时用户动作记录。
- 临时规则库和样例库索引。

飞书不存放：

- 大量全文。
- 视频文件。
- 图片文件原件。
- 全量评论原文。
- Whisper 分段转录原文。
- 历史版本全文。

### 14.2 运行期字段责任方

飞书表格字段的责任方只允许三类，不出现 Codex。

| 责任方 | 含义 | 示例字段 |
|---|---|---|
| 脚本生成 | 由 CLI、同步脚本、定时任务或确定性程序生成 | 内部 ID、原始链接、抓取时间、平台指标、抓取状态、错误码、内容哈希、RAG Document ID |
| Hermes维护 | 由 Hermes 运行期生成、补充或维护 | AI 摘要、热点状态、拆解结论、沉淀建议、选题补充、卡片摘要、规则候选 |
| 人工 | 由内容+技术（内部群）或社群成员显式操作 | 是否启用、等级、是否沉淀、选题标题、是否采纳、拒绝原因、显式规则 |

字段配置需要预留删改能力：

1. 每张表必须有 `schema_version`。
2. 字段新增、删除、重命名应通过配置文件或迁移脚本管理。
3. 字段删除前应先进入 `deprecated` 状态，不直接物理删除。
4. Hermes 读取表结构时应允许字段缺失，并通过字段映射配置降级处理。
5. 卡片表字段应与内部字段解耦，避免内部表调整直接破坏外部展示。

飞书 CLI 使用规则：

1. v1 优先采用官方 Lark/Feishu CLI（`lark-cli`）读写飞书 Base / 多维表格。
2. 当 `lark-cli` 不覆盖必要能力时，允许使用官方 API 薄脚本兜底。
3. 不自研 Feishu Adapter 或 Bitable Adapter；只保留 `lark-cli` / 官方 API 调用脚本、字段映射和幂等写入规则。
4. 外部群不开放内部表权限，卡片表也不开放社群成员编辑权限。
5. 对外只写表 9 卡片表；外部反馈入口由人工主导优化，不在 v1 设计复杂反馈系统。

### 14.15 表 12：样例库

样例库用于临时保存用户如何改标题、如何采纳、如何拒绝、如何定义好选题的实例。

| 字段 | 类型 | 责任方 | 说明 |
|---|---|---|---|
| 样例 ID | 文本 | 脚本生成 | 唯一 ID。 |
| 样例类型 | 单选 | 人工 / Hermes维护 | 采纳样例 / 拒绝样例 / 标题修改样例 / 角度修改样例 / 规则样例。 |
| 输入上下文 | 长文本 | 脚本生成 / Hermes维护 | 原素材、热点、对标内容摘要。 |
| Hermes 原建议 | 长文本 | Hermes维护 | 如有。 |
| 用户最终版本 | 长文本 | 人工 | 用户修改后的标题、角度或判断。 |
| 用户原因 | 长文本 | 人工 | 采纳、拒绝或修改原因。 |
| Hermes 归纳 | 长文本 | Hermes维护 | 抽象出的偏好或反例。 |
| 关联规则 | 关联 | 人工 / Hermes维护 | 关联规则库。 |
| 是否可用于提示词样例 | 勾选 | 人工 | 必须人工确认。 |
| 是否可用于 RAG | 勾选 | 人工 | 必须人工确认。 |

生命周期规则：表 12 的正例、反例和修改前后样例，可作为完整 Skill 样例目录来源；是否迁移、何时取消或只读归档，由内容+技术（内部群）在 v4 或 v5 人工决议。

### 14.16 Hermes 观察用户选题机制

本项目要求：Hermes 不直接“学习用户”，不做不可审计、不可回滚的隐式偏好更新。

Hermes 的观察流程：

```text
用户查看卡片 / 修改选题标题 / 采纳选题 / 拒绝选题 / 提交显式规则
  ↓
脚本生成用户动作日志
  ↓
Hermes 归纳动作原因、偏好、反例和规则候选
  ↓
写入临时规则库与样例库
  ↓
内容+技术（内部群）人工审核
  ↓
人工筛选稳定规则、正例和反例
  ↓
沉淀为版本化选题筛选 Skill
  ↓
v4/v5 人工决议是否取消表 10-12 或转为只读归档
```

Hermes 能力演进分为四个阶段：

| 阶段 | Hermes 角色 | 允许动作 | 人工要求 |
|---|---|---|---|
| 阶段 1 | 观察者 | 记录用户动作、归纳拒绝原因、生成规则候选 | 必须人工确认规则。 |
| 阶段 2 | 建议者 | 根据临时规则库和样例库补充选题字段、卡片摘要和推荐理由 | 人工决定是否采纳。 |
| 阶段 3 | 受控执行者 | 对稳定规则覆盖的场景自动生成候选卡片或选题补充 | 人工可回滚，规则可审计。 |
| 阶段 4 | 执行者 | 对高稳定、低风险、明确边界的任务自动执行 | 需单独版本确认，v1 不启用。 |

### 14.17 v1 主工作台

v1 的主工作台不是单一表，而是内部多维表 + 卡片表两层：

1. **内部主工作台**：表 4 对标内容拆解表、表 6 素材沉淀表、表 7 选题池表；表 5 热点雷达表进入 v2。
2. **外部主工作台**：表 9 卡片表。
3. **运行维护工作台**：表 1 信息源表、表 2 数据源健康表、表 3 对标账号表。
4. **临时观察工作台**：表 10 用户动作日志表、表 11 可审计规则库、表 12 样例库；v4/v5 由人工决定是否大版本取消并迁移为 Skill。

## 15. 选题生成原则

### 15.1 v1 不强制每日产出数量

选题生成以对标账号内容沉淀质量为前提。若当天对标账号更新弱，系统可以只输出观察摘要，不强行生成低质量选题。

### 15.2 选题生成启动条件

v1 先建选题池表，但在“选题筛选 Skill 策略”完成前，Hermes 不自动把素材直接转成正式选题。

过渡期规则：

1. 用户维护选题池中的“选题标题”字段。
2. Hermes 基于该标题补充推荐理由、关联素材、目标平台、核心钩子、简要大纲、证据链和卡片摘要。
3. Hermes 观察用户如何写标题、如何修改标题、如何采纳、如何拒绝，并把动作写入用户动作日志、临时规则库和样例库。
4. Hermes 可以给出“候选草稿”或“补充建议”，但不直接替用户决定正式选题标题。
5. 表 7 可生成外部选题卡，但 v1 暂定以人工维护标题为主。

正式启动条件：

1. 已完成对标账号每日跟踪链路。
2. 已完成对标内容结构化采集、转录、拆解和卡片生成。
3. 已完成基础去重。
4. 已完成选题筛选 Skill 策略。
5. 临时规则库中有足够稳定的可审计规则和样例。
6. Hermes 可以基于该 Skill 输出稳定格式的候选选题。

在正式启动条件满足前，trend-chief 主要输出：

- 对标账号更新摘要。
- 高表现内容提醒。
- 可供人工判断的素材记录。
- 对用户选题标题的补充说明。


### 15.3 选题来源

v1 选题来源只保留对标型；热点型和融合型进入 v2。

1. **对标型**：由对标账号高表现内容、新内容模式或人工标记内容触发。
2. **热点型，v2**：由及时热点、潜在热点或上升热点触发。
3. **融合型，v2**：由热点信号与对标账号内容模式共同触发。

### 15.4 选题卡最低内容

进入选题池的选题建议至少包含：

- 选题标题，v1 优先由人工维护。
- 来源类型。
- 关联对标内容；关联热点为 v2 字段。
- 目标平台：抖音 / 小红书。
- 推荐理由。
- 核心钩子。
- 简要内容大纲。
- 证据链接。
- Hermes 判断。
- 当前状态。


### 15.5 选题筛选 Skill 的实现边界

选题筛选 Skill 分为三部分：

| 部分 | 责任方 | 说明 |
|---|---|---|
| Skill 工具与脚本生成 | 脚本生成 | 运行 Prompt 文件结构、输入输出 Schema、测试样例、版本号、CLI / MCP 调用入口。 |
| Skill 运行管理 | Hermes维护 | 在日报、热点提醒和选题补充中调用 Skill，并根据 Skill 输出生成建议字段。 |
| Skill 策略确认 | 人工 | v1 确认什么样的对标内容可以进入候选选题，确认规则是否启用；热点策略进入 v2。 |

规则：

1. Skill 未完成前，Hermes 不正式提交选题，只沉淀素材和观察。
2. Skill 文件必须版本化，例如 `selection_skill_version = v0.1`。
3. 每条选题候选必须记录使用的 Skill 版本。
4. 修改 Skill 需要通过仓库配置或脚本变更完成，由内容+技术（内部群）确认后启用。
5. 完整 Skill 必须包含可运行规则、输入输出 Schema、正例、反例、标题修改样例和拒绝样例。
6. 表 10-12 迁移到 Skill 只能人工进行；Hermes 可以建议候选规则和候选样例，但不能自动启用。
7. 表 10-12 是否在大版本中取消或转为只读归档，由内容+技术（内部群）在 v4 或 v5 人工决议。

## 16. 复盘与风险审核边界

### 16.1 复盘边界

v1 暂不考虑发布复盘。

原因：

- 当前阶段还未沉淀足够选题。
- 需要先验证对标账号追踪、热点信息沉淀和选题生成链路。
- 等内容规模达到一定量后，再设计内部账号复盘、评比和基于发布表现的 Agent 学习机制；这不影响 v1 通过临时观察表沉淀选题 Skill。

发布复盘表仅作为占位表保留。

### 16.2 风险审核边界

v1 面向 AI 赛道，暂不设置严格风险审核边界。

保留以下扩展字段：

- `risk_level`
- `risk_tags`
- `risk_reason`
- `requires_manual_review`

后续扩展到医疗、金融、法律、教育、政策等赛道时，再加入完整风险审核规则。

## 17. 非功能需求

### 17.1 可观测性

系统必须记录：

- 每次抓取任务。
- 每次 Hermes 分析任务。
- 每次飞书写入任务。
- 每次 Whisper 转录任务。
- 每次 RAG 导出任务。
- 每次失败与重试。

### 17.2 数据可追溯

飞书中的每条热点、对标拆解和选题建议，必须能追溯到：

- 原始来源链接。
- 本地 DB 对象 ID。
- Hermes 分析任务 ID。
- 抓取时间。
- 写入飞书时间。

### 17.3 成本控制

v1 建议采用分层分析策略：

1. 规则初筛。
2. 关键词与标签归类。
3. 只对高价值内容调用 Hermes 深度分析。
4. Whisper 只转录对标账号视频和进入候选池的视频。
5. AI 分析结果缓存。

### 17.4 开源可部署性

项目开源后，应尽量支持：

- 本地部署。
- Docker Compose。
- `.env` 配置。
- 示例数据。
- 示例飞书表结构。
- 示例信息源配置。
- 示例对标账号配置。
- 运行日志。
- 最小可运行 demo。
